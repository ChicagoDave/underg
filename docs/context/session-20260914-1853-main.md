### Phase 3 — World authoring in Chord (STARTED, now BLOCKED)
- **BLOCKER G9**: Chord cannot give two entities the same printed name. Verified fresh at summary time by building `spikes/duplicate-names/duplicate-names.story` (two rooms both named "the Mine"): `npx sharpee build` fails with `error [analysis.duplicate-entity] An entity named 'mine' is already declared at line 10` — the load-time gate refuses it outright, and the grammar has no construct separating an entity's identifier from its display name.

- `docs/work/port-underground-v1-chord/chord-gap-g9.md` — the gap write-up for the sharpee repo. Key evidence: IREntity already carries `id` and `name` as separate fields, and the duplicate gate keys on the name only because the id is derived from it (`analyzer.ts:3897`). So the model already draws the distinction; only the surface syntax is missing. Candidate shape: a `named` line inside the create block, additive, a minor bump to Chord 3.7.0 by ADR-257 D2.

## Key Decisions

### 1. Placement: self-contained in this repo
The port is not a branch-story in `~/repos/sharpee`. Chord is consumed as published npm packages (devkit/chord/branch-tester all at 5.4.1, language 3.6.0). Consequence: a language gap this port finds is a change in `sharpee` that must be published before this repo can consume it — Phase 2's mapping table records gaps against the published surface, not the monorepo working tree. Recorded in the plan, not an ADR (user: "no ADR - we use devkit in this repo. it suffices").

### 2. Line-975 bug: keep the upstream restoration
`original/UNDERG.BAS` carries `975 ON ERROR GOTO 0`, restored upstream. Kept as-is rather than fixed: the oracle and the port read the same source, so parity holds by construction; the bug only misreports a failed `CHAIN` at line 990 and has no Chord analogue (no `CHAIN` to fail). Recorded in the plan's deviation-ledger notes as an upstream restoration, not a port deviation. Also not an ADR, per the same user decision above.
